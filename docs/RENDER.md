# Deploying Zenora to Render (free tier, for testing)

This puts the whole app on the internet for **testing and demos**, at no cost. It is not for real customers: see "What free means" below. The blueprint is `render.yaml` at the repo root.

What I checked: the build commands, migration step and start commands in `render.yaml` were run from a **fresh clone** of the repo (install, build of API, worker and web, migration check), and the three services were started the way Render will start them (`PORT` set, `NODE_ENV=production`, cross-site cookie on). Health checks answered, signup/login set `HttpOnly; Secure; SameSite=None`, and the production security headers were present. What I could **not** check: Render itself (no account), and the Linux build image.

## What you need first (all free)

| Thing | Where | Notes |
|---|---|---|
| GitHub repo Render can read | github.com | The repo is `Rookiezz-Solution/Zenora`. Render needs access to it (private is fine). |
| Postgres database | neon.tech | Create a **new project just for testing**; do not reuse your development database. Copy the **pooled** connection string. |
| Redis | upstash.com | Create a database; copy the `rediss://...` URL (the TLS one). |
| Render account | render.com | Sign in with GitHub. |

## Steps

1. **Create the database and Redis** (above). Keep both connection strings handy.
2. **Make two secrets** on your machine:
   - `TOKEN_ENCRYPTION_KEY`: run `openssl rand -hex 32` (64 hex characters). **Save it somewhere safe**: losing it makes every stored channel token and integration key unreadable.
   - (`AUTH_SECRET` is generated by Render for you.)
3. In Render: **New → Blueprint**, pick the repo. Render reads `render.yaml` and proposes three services (`zenora-api`, `zenora-worker`, `zenora-web`) and one shared environment group (`zenora-shared`).
4. Render asks for the values marked `sync: false`. Fill in:
   - `DATABASE_URL`: the Neon pooled string.
   - `REDIS_URL`: the Upstash `rediss://` URL.
   - `TOKEN_ENCRYPTION_KEY`: the 64-hex value from step 2.
   - `SUPER_ADMIN_EMAILS`: your email (lets you open `/admin`).
   - `NEXT_PUBLIC_SUPPORT_EMAIL`: optional.
5. Click **Apply**. The first build takes several minutes per service. The API's build also runs the database migrations, so the Neon database is filled in automatically.
6. **Check the real addresses.** The blueprint assumes `https://zenora-web.onrender.com` and `https://zenora-api.onrender.com`. If Render had to add a suffix (names are global), open each service's page, copy its real URL and set:
   - on `zenora-api`: `APP_URL` = the web URL, `API_URL` = the API URL;
   - on `zenora-web`: `NEXT_PUBLIC_API_URL` = the API URL, then **Manual Deploy → Clear build cache & deploy** (this value is baked in at build time).
7. Open the web URL, sign up, and walk through it. `https://<api>/health/ready` should say `database: up, redis: up`; `worker` shows `up` once the worker service is running.

## What free means (read this)

- **Services sleep** after about 15 minutes with no visitors; the next request waits ~30–60 seconds. The **worker sleeps too**, so reminders, the daily trial/credit sweep, ad sync and queued webhook processing pause until something wakes it. For a demo that is fine.
- **Free instance hours are limited** (Render gives a monthly allowance shared across your free services). Three services kept awake all month would exceed it; sleeping is what makes free work. A pinger that keeps them awake (UptimeRobot, cron-job.org) will use the hours up faster.
- **Memory is small (512 MB)** and builds can run out of memory on the free plan. If the web build fails with an out-of-memory error, that is a free-tier limit, not a code fault: retry, or use a paid instance for the build.
- **Cookies:** the web app and API are on different `*.onrender.com` sites, so the login cookie is `SameSite=None; Secure`. Chrome, Edge and Firefox accept this; **Safari and some privacy settings block third-party cookies**, so login may not stick there. This disappears on your own domain.
- **Free Postgres/Redis (Neon/Upstash) are for testing**: small limits, little backup history.
- Realtime inbox updates use a WebSocket to the API; it should work but has not been tried on Render.

## Not set up here (add later in the app)

- Email (verification, password reset, invites): add an SMTP server under **Admin → Integrations → Email (SMTP)**. Until then password reset says it can't send.
- Meta (WhatsApp/Instagram), Google, Razorpay, Anthropic: enter keys under **Admin → Integrations**. Register the redirect URLs it shows (they use your API URL), and use Razorpay **test** mode while testing.
- A custom domain: in Render, add `app.yourdomain.com` to the web service and `api.yourdomain.com` to the API, update the three URLs, and **delete `SESSION_COOKIE_SAMESITE`** (so cookies are `Lax` again).

## Going from testing to real customers

Move to paid instances (so nothing sleeps and the worker always runs), paid Neon with point-in-time backups, your own domain and an SMTP provider, then work through `docs/DEPLOYMENT.md` (backups, secret rotation, monitoring) and `docs/SECURITY.md`. Do not take real payments or customer data on the free setup.
