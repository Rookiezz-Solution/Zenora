## 2026-10-03 — Phase 2 item 4: Custom trigger builder (tag_added event, AND conditions, limits, My triggers)

**Scope decision**: docs/PRD.md's Growth-section bullet is "any event (Instagram, WhatsApp, CRM, calls/calendar, payments/forms, schedule, date field, webhook/API) + AND/OR conditions on any field + limits (once per lead, working hours, delay); save to 'My triggers'". Most of those event sources don't exist yet (calls/calendar/forms), need a public API (webhook/API — Phase 3), or need a new third-party service, so this item builds a coherent v1 slice and logs the rest rather than half-building it. No new third-party service, billing, privacy or Meta-policy change, so no check-in was needed. (This item was started in a session that hit a usage limit mid-way and finished in the next one — the first batch of edits sat uncommitted until then.)

**Done**
- **New CRM event source: `tag_added`** — fires when a tag is newly added to a lead (`LeadsService.addTag`; re-adding a tag the lead already has doesn't fire; a trigger failure never fails the tagging). Config: a tag name, or empty for "any tag".
- **AND conditions on any trigger** — extra conditions (source / tag / custom field × equals / contains) that must all match the lead, for the new event *and* the existing WhatsApp/Instagram keyword triggers. Reuses routing's `RoutingCondition`/`matchesCondition` directly rather than adding a fourth condition-matching shape (all in `packages/shared`, so no DI-boundary reason to duplicate).
- **Limits**: `onceForLead` (never re-run for a lead, even after a run completes — the old behavior only blocked while a run was in progress, which stays the default) and `delayMinutes` (delayed BullMQ job). Pure helpers `isTriggerAllowedToFire`/`triggerDelayMs` in `packages/shared/src/automation.ts` are shared by both matchers.
- **Two matchers, same logic**: `apps/worker/.../trigger-matcher.ts` (message keywords; rewritten to apply conditions/limits and return each match with `delayMs`) and a new `apps/api/.../trigger-events.service.ts` (CRM events originate from API actions, not webhooks). The API enqueues the same `automation-engine` "start" job the worker's message processors use — the worker doesn't care who produced it. `enqueueStart` gained a delay param; the WhatsApp/Instagram processors pass `delayMs` through.
- **"My triggers"** — `SavedTrigger` gained the `type` column it was missing (migration applied); new `GET/POST/DELETE .../automations/:ws/saved-triggers` (declared before `:id` so the path isn't swallowed as an id). `setTriggerSchema` is now a proper `discriminatedUnion` on trigger type (it used to validate every type against the keyword shape, which couldn't survive a second type).
- **UI**: the automation editor's trigger box is now a `TriggerEditor` component — trigger-type picker (WhatsApp message / Instagram DM / Tag added), conditions rows (with custom-field picker), once-per-lead checkbox, delay input, "Save to My triggers", and a load/delete dropdown for saved ones. UI-state ↔ API-payload mapping lives in `apps/web/src/lib/trigger-definition.ts`.
- Tests: 7 shared (`automation.test.ts`), 6 new worker matcher cases (conditions, onceForLead, completed-vs-running, delay, no-lead-query-when-unneeded) plus updated processor tests asserting the delay is passed to `enqueueStart`, 7 `TriggerEventsService`, 3 `addTag`, 3 `setTrigger`/saved-trigger — 256 total across the repo (shared 46, worker 55, api 155). Full `pnpm typecheck`/`lint`/`test`/`build` green.

**Simplifications / follow-ups**

- **Working-hours limit** is deferred — the workspace has no working-hours schema yet (that needs its own settings UI first).
